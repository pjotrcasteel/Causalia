Causalia in 30 seconds

The bug is not always in the code.
Sometimes it is in the ordering.

A retry arrives after a commit. Two workers save the same version. A process dies between durable steps. Ordinary tests often see one friendly ordering. Causalia explores the unfriendly ones on purpose.

01

State the guarantee

“This payment happens once.” “Only one writer wins.” “Recovery never repeats completed work.”

02

Explore the difficult paths

Control virtual time, scheduling, retries and modeled failure semantics instead of waiting for a race to happen.

03

Keep the exact failure

Capture the replay, fix the code, rerun that same path and keep it in the regression suite.

A Causalia-aware debugging prompt

Use this as a starting instruction for an agent working in a .NET solution that can install or already uses Causalia.

When investigating timing, retry, duplicate-delivery, restart, or concurrency risk in this .NET solution:

1. Run "dotnet causalia inspect <solution> --format json" and use the findings as leads, not conclusions.
2. Choose one high-value production boundary and state the business invariant that must hold.
3. Prefer normal .NET seams such as TimeProvider, CancellationToken and narrow dependency interfaces.
4. Add a focused deterministic Causalia simulation around that boundary.
5. If a failure is found, preserve the replay token and reduced failure sequence.
6. Make the smallest production fix supported by the evidence.
7. Replay the exact failure, then run broader exploration and the existing test suite.
8. Keep real infrastructure integration tests; do not claim modeled provider semantics prove the real provider.

Do not spread Causalia runtime types through the domain/application layer unless the simulation boundary genuinely requires it.

No magic, no mystery

What Causalia is — and what it isn't.

Does Causalia replace integration or end-to-end tests?

No. Causalia verifies the semantics you model under controlled timing and failure conditions. Keep real-provider integration tests for actual databases, brokers, HTTP stacks and infrastructure.

Does production code need to depend on Causalia?

Prefer not to. Use normal .NET seams such as TimeProvider, CancellationToken and narrow storage/messaging/HTTP interfaces, then place simulated adapters in the test project.

What does deterministic mean here?

The simulation controls relevant sources of time and scheduling so a discovered execution can be replayed instead of depending on wall-clock luck.

Can AI coding agents use Causalia?

Yes, when the agent can run commands and tests in the workspace. Structured inspection output plus exact replay gives the agent a more stable debugging loop than repeatedly chasing a flaky failure.

When is Causalia probably the wrong tool?

Simple CRUD with no meaningful concurrency or partial-failure behavior, provider certification, and real performance/load benchmarking are usually better served by ordinary tests and provider-specific tooling.

Does a Causalia trace prove root cause?

No. It is evidence. Failure minimization and analysis can help identify what the reproduction depends on, but the trace should not be treated as an automatic causal claim.
