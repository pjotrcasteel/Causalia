# Causalia 2.2.0 architecture audit and implementation plan

Status: audit and first typed-fault increment; **not release ready**.

## 2.1.1 audit

- `DeterministicScheduler` owns logical time, execution choices, tracing, invariants and isolated random streams. Adapter operations use `SimulationContext.TimeProvider`, `Task.Yield` and cancellation, so vendor delivery must be represented as scheduled logical events, never wall-clock timers.
- `FaultPlan<TContext, TEffect>` is an ordered list of policies. `SimulationContext.CreateFaultInjector` binds it to a deterministic scope and seed. `FaultInjector` evaluates each policy with its own derived random seed, while the execution controller records/suppresses occurrences for replay and minimization. New DSL rules must feed this same path.
- Adapters are separate net10 projects referencing core. RabbitMQ and Kafka use concrete brokers/clusters, context extension factories, adapter-specific fault plans and string trace entries. Dapr follows the same composition pattern. Rabbit models queue acknowledgement/redelivery; Kafka models committed offsets and group membership. Neither is an Azure Service Bus compatibility layer.
- `dotnet causalia inspect` resolves project/solution inputs, scans source for token/pattern findings and ranks boundaries. `init` selects a project and writes a compiling green test project. `generate` should reuse target resolution, findings and generated project layout, adding conservative boundary-specific tests without fabricating application behavior.
- Analyzers enforce deterministic behavior only inside simulation boundaries; inspection is an adoption heuristic rather than full compiler semantic analysis. Generation must label its confidence and leave application wiring explicit.
- `SimulationReproduction`, scheduler choices and fault occurrences form replay/minimization inputs. `FailureAnalyzer` classifies reduced failures. Adapter state needs to be simulation-local and recreated on replay; no static counters or side effects outside the scheduler.
- Visualization consumes `SimulationResult` or `SimulationFailedException` trace entries and fault summaries. Its trace is currently textual. Consistent event labels can improve presentation additively; changing trace serialization would risk replay compatibility.
- Public APIs to preserve: `Simulation.RunAsync`, `SimulationContext`, `FaultPlan`/`IFaultPolicy`, existing adapter factories and plans, CLI `inspect`/`init`, replay tokens and trace document contracts. Missing extension points: typed event matching with scoped occurrence counts; Azure settlement outcomes; structured trace categories; generation-safe boundary metadata.

## Decisions and milestones

1. Extend `FaultPlan<TContext,TEffect>` additively with typed `On<TEvent>` rules, retaining `FaultInjector` and existing policy evaluation. Rule occurrence state is per injector so replay runs do not share one-shot state. Prove ordering, filtering, replay and minimization before adapters use it.
2. Add `Causalia.AzureServiceBus` as a deterministic logical broker. Separate queue and subscription entities, immutable message envelope and delivery handle. Model PeekLock, lock token/generation, virtual expiration/renewal, Complete/Abandon/DeadLetter, scheduled availability, max delivery count and DLQ. Settlement-ack-loss is applied *after broker state commits*; redelivery then requires an additional explicitly modeled ambiguity (for example stale client replay or settlement not committed). **A successfully completed message must not be redelivered solely because its acknowledgement was lost.** The requested sequence conflates successful settlement and failed settlement; tests should cover both distinct outcomes. Defer sessions unless ownership and ordering can be expressed without an emulator.
3. Offer typed rule helpers for existing adapter event contexts only where semantics are already exposed, retaining legacy plans.
4. Add `generate` through inspection and init components. Deterministic ordering and stable names; generate compileable tests that assert simulation mechanics and TODOs for application-specific assertions, never a misleading business invariant. Identify Azure SDK, EF/storage, HTTP, TimeProvider and broker markers. Compile a fixture project as a release gate.
5. Add only delivery, settlement, lock and fault trace presentation with existing trace contracts. Keep visualization optional.
6. Run full build/tests, package consumer verification, benchmarks, analyzer checks and documentation review. Advance package versions to 2.2.0 only after all gates pass.

## Compatibility and limitations

All planned public additions are additive. No core engine rewrite or vendor SDK dependency is required for the simulation package. The existing source inspection is heuristic; unknown wrapper abstractions require a TODO and explicit user wiring. Real namespace conformance remains covered by separate integration tests.

## Current implementation snapshot

- Typed `FaultPlan.On<TEvent>(name).Where(...).Once()/Times(...).Apply(...)` delegates to `FaultInjector`; existing policies remain valid. The current API is an incremental typed rule builder, not the finished cross-adapter scenario vocabulary.
- Azure Service Bus package models queues, fanout subscriptions, scheduled visibility, PeekLock, Complete, Abandon, DeadLetter, expiry, renewal, delivery count and committed-versus-rejected settlement faults. It uses the existing trace and replay inputs. Sessions, receiver close/process lifecycle, session ordering and automatic lock timers are not yet implemented. Lock expiry is observed on receive/renew/settle; it is based on virtual time.
- `generate` reuses `init` and `inspect`, emitting stable per-boundary compileable skeletons with explicit application wiring TODOs. It does not yet generate actual application-invoking tests, identify commit/publish sequencing, concurrency races or process restart points from semantic analysis.
- Visualization receives readable `servicebus:*` trace events through its existing pipeline; no structured causal edges or specialized event renderer has been added.

## Example API

```csharp
var faults = new FaultPlan<ServiceBusSettlementEvent, ServiceBusSettlementFault>();
faults.On<ServiceBusSettlementEvent>("lost-complete-ack")
    .Where(e => e.Action == ServiceBusSettlementAction.Complete)
    .Once()
    .Apply(_ => ServiceBusSettlementFault.LoseAcknowledgement);

var bus = context.CreateAzureServiceBus(faults);
bus.CreateQueue("orders");
await bus.SendAsync("orders", payload, null, context.CancellationToken);
var delivery = await bus.ReceiveAsync("orders", context.CancellationToken);
await bus.CompleteAsync("orders", delivery!, context.CancellationToken);
```

```shell
dotnet causalia inspect Orders.slnx
dotnet causalia generate Orders.slnx --project src/Orders/Orders.csproj
```

## Draft release notes (pending completion)

Causalia 2.2.0 introduces a typed rule builder over the existing replayable fault injector, a deterministic Azure Service Bus simulation package for common PeekLock delivery and settlement failures, and `dotnet causalia generate` for conservative boundary test scaffolding. The release preserves existing core and adapter APIs. The generated test project includes explicit TODOs for real application wiring. Service Bus sessions and vendor-specific broker behaviors remain outside the simulation model.

## Performance observation

The full test solution completed successfully in this environment; no dedicated benchmark baseline was collected, so no throughput or allocation claim is justified yet.

## Completed hardening work

- Session ownership uses virtual-time exclusive leases. Disposing the receiver releases unsettled message locks; the logical broker survives process generations.
- Azure settlement replay/minimization regression removes an irrelevant fault and reproduces the same failure with the minimized token.
- Visualization classifies Service Bus events in an entity lane, correlates delivery and settlement by message sequence, and highlights lock expiry and lost acknowledgement.
- `generate` emits a typed Service Bus redelivery skeleton for a discovered Service Bus boundary. The packaged tool's isolated consumer compiles and executes this generated project. Other boundaries remain explicit TODO skeletons.
- Release build and full 295-test solution pass. `eng/verify.py --packages ... --consumer` verifies 15 packages, 13 symbol packages, the packaged analyzer and installed tool commands. All pre-existing packages pass `PackageValidationBaselineVersion=2.1.1` pack checks.
- The repeatable 1000-scenario performance baseline is in `artifacts/2.2.0-BENCHMARK-BASELINE.json` and its source is `benchmarks/Causalia.Benchmarks`.

## Deliberate limitations

The generator cannot safely invoke an arbitrary application handler without knowing its constructor graph and domain input; it leaves that wiring and invariant as explicit TODOs. Sessions model ownership and ordered delivery, not vendor protocol details such as filters, transactions, deferral, auto-forwarding, batching or partitioning. Real Azure SDK integration remains a separate integration test concern.
